Privacy Policy

ParticipantFlow for JSM

Vendor Seisuke Nagahara Effective September 14, 2026 Contact support@asunoki.jp

ParticipantFlow for JSM (the “App”) is an Atlassian Forge app for Jira Service Management Cloud. This policy explains what data the App touches when a customer runs it, and what it does not do with that data.

In short: the App has no server of its own, no database, and no analytics. It runs entirely inside Atlassian’s Forge platform, reads and updates a Jira Service Management request’s Request Participants at the moment an Automation rule invokes it, and returns a result back into that same rule. Nothing is stored, logged, or sent anywhere outside Atlassian’s infrastructure.

01 What the App is

The App adds one action to Jira Automation: Add Request Participants (ParticipantFlow for JSM). Given a Request/Issue key and a source (a Jira group, an email list, or a list of Account IDs), it adds the resulting people to that request’s Request Participants — without ever removing anyone already there — and returns counts and identifiers for the rest of the Automation rule to use.

02 Data the App reads and writes

Each time the action runs, for the single request specified by the Automation rule, it:

  • Reads the request’s existence and the running user’s access to it.
  • Reads the request’s current Request Participants (Account IDs only) to determine who is already present.
  • If the source is a Jira group: reads that group’s membership (Account IDs) via Atlassian’s Jira API.
  • If the source is an email list: sends each email address to Atlassian’s own Jira user-search API to resolve it to an Account ID. Ambiguous or no-match results are treated as unresolved and are not added.
  • Writes the resolved Account IDs to the request’s Request Participants, additively only.

03 Data the App does not collect

  • No account credentials, API tokens, or secrets — authentication is handled entirely by Forge’s built-in identity (asUser()); the App never sees a password or token.
  • No persistent storage. The App uses no Forge Storage, no external database, and no file storage. Data exists only in memory for the duration of a single Automation step and is discarded immediately after.
  • No analytics, telemetry, or usage tracking beyond what the Forge platform itself provides to all Forge apps for operational health.
  • No cookies, because the App has no web-facing pages of its own outside the Jira Automation configuration screen it renders through Atlassian’s UI Kit.
  • The App’s own operational logs record only counts and status (for example, how many participants were added) — email addresses and other personal identifiers submitted as input are never written to logs.

04 Where processing happens

The App runs as a Forge function hosted by Atlassian. It never calls any server operated by the vendor, and it never sends data to any third party. The only network calls the App makes are to Jira’s own REST APIs, within the same Atlassian Cloud site that installed it. Data residency therefore follows the customer’s own Atlassian Cloud data-residency configuration; the App has no infrastructure of its own to introduce a separate region.

05 Permission scopes requested

ScopePurpose
read:servicedesk-requestRead a Jira Service Management request and its current Request Participants, and confirm the running user’s access to it.
write:servicedesk-requestAdd Account IDs to a request’s Request Participants.
read:jira-userResolve an email address to an Account ID when the email-list source is used.
manage:jira-configurationRead Jira group membership when the group source is used. This scope is required by Atlassian’s own Group Members API for this operation; there is no lighter-weight alternative scope.

These are the only scopes the App requests. Every one of them is used only to read or add data the customer explicitly asked the Automation rule to act on; the App cannot create, delete, or modify anything else in Jira.

06 Subprocessors

None. The App integrates no third-party service, analytics vendor, email provider, or storage provider of its own. The only infrastructure involved is Atlassian’s own Forge platform, which is already covered by Atlassian’s own privacy and security commitments to the customer.

07 Your rights & data requests

Because the App retains nothing after each Automation run completes, there is no App-held personal data to access, export, or delete. Account IDs added as Request Participants are retained only by the customer’s own Jira Service Management site, under the customer’s own control.
