Vendor Seisuke Nagahara Version 2.5.0 Contact support@asunoki.jp

ParticipantFlow for JSM adds one action to Jira Automation: Add Request Participants (ParticipantFlow for JSM). This page covers how to add it to a rule, what each setting does, its output Smart Values, and troubleshooting.

01 Adding the action to a rule

  1. Open the Jira Service Management project you want to automate, then go to Project settings → Automation (or a global rule under Jira settings → System → Automation rules).
  2. Create or edit a rule. Add any trigger that gives you a Service Management request — for example Manual trigger, Issue created, or Issue transitioned.
  3. Add a new action and search for Add Request Participants (ParticipantFlow for JSM).
  4. The first time you use the action, click Connect to authorize it — no API token or password is required.
  5. Fill in the fields described below, then save the step.
  6. Add further actions (for example Send email or Add comment) that use the action’s output.

02 Action settings

FieldWhat it does
Issue KeyThe Service Management request to update. Usually left as {{issue.key}} so the action runs against the issue the rule is triggered on.
SourceWhich of the three inputs below to use: group, emails, or accountIds.
Group name or Group IDUsed when Source is group. Every member of the group is added. Requires the rule’s actor to have Jira administrator permission (see note below).
Email listUsed when Source is emails. Comma or newline separated. Each address is resolved to an Account ID; unresolved addresses are skipped and reported, not treated as errors.
Account ID listUsed when Source is accountIds. Comma or newline separated Account IDs, added directly.

Existing participants are never removed. The action always reads the current Request Participants first and only adds the difference. Running the same rule twice on the same request never creates duplicates.

03 Using the output

Automation names the action’s output after the action itself, camelCased from the entity name declared in the app. Check the exact Smart Value name Automation shows for your specific step (it can vary rule to rule), then reference the fields below, for example {{addRequestParticipantsResult.addedCount}}:

Smart Value fieldContents
addedCountHow many participants were newly added in this run.
skippedCountHow many were already participants, so were skipped (not duplicated).
failedCountHow many inputs could not be resolved or added.
addedAccountIdsComma-separated list of the Account IDs actually added.
failedValuesComma-separated list of the inputs that failed, with the reason.
summaryA one-line, human-readable summary of the result.

Example: notify on partial failure

Condition: {{addRequestParticipantsResult.failedCount}} > 0

Action: Add comment (internal only)
Some participants could not be added: {{addRequestParticipantsResult.failedValues}}

04 Troubleshooting

  • Everything in the email list fails. JSM customer-only (portal-only) accounts are sometimes not resolvable through Jira’s standard user-search API, depending on profile visibility and site configuration — this is a known limitation of the underlying Atlassian API, not an app bug. Try the Account ID source instead if you already know the Account ID.
  • Group source returns a permission error. Reading Jira group membership requires the Automation rule’s actor to have Jira administrator permission — this is required by Atlassian’s own Group Members API. Check the rule’s Actor setting under Settings.
  • A large group only added the first 500 members. This is an intentional safety cap to keep the action within Forge’s execution time limits. Split very large groups into smaller ones if you need to add more than 500 people in a single run.
  • Smart Value shows literally as text instead of a value. The entity name in your rule differs from the example above — open the action step in the rule editor to see the exact name Automation assigned it.
